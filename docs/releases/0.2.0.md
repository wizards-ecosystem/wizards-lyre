# The Wizard's Lyre 0.2.0

Lyre still runs ACE-Step 1.5 on your own GPU by default. This release adds an
opt-in **Remote GPU lane** for when you do not have a suitable card: the same
ACE-Step 1.5, driven by the same adapter, on a GPU you rent or run elsewhere,
while your projects and takes stay on your machine. Lyre can start and stop a
Runpod pod for you, and it only ever rents one when you press Start.

## Install or update

Download `wizards-lyre-0.2.0-linux-x86_64.tar.gz` or the matching `.zip`, plus
`SHA256SUMS`, from the assets below, verify, extract, and run:

```bash
sha256sum --ignore-missing --check SHA256SUMS
./scripts/lyre bootstrap
./scripts/lyre doctor
```

Nothing changes for a local-only install. Projects from 0.1.0 open unchanged.

## Highlights

- **Remote GPU lane.** Start the worker with `LYRE_WORKER=remote` and renders
  go to an ACE-Step host over HTTPS with a shared secret. The queue, the GPU
  lease, and every take stay local. Generate, cover, repaint, extract, lego,
  and complete work remotely; style packs stay local for now.
- **Runpod provisioner.** With `LYRE_REMOTE_GPU_PROVISIONER=runpod` and a key in
  `.env`, the Remote GPU panel shows the hourly rate before you start, the
  spend while it runs, and terminates the pod on Stop or a clean exit. Nothing
  rents hardware on its own, and a pod a crash left behind is reported at the
  next start.
- **A published host image**, `ghcr.io/wizards-ecosystem/wizards-lyre-remote-gpu`,
  tagged by build id, so a Runpod user needs a key, not Docker and a registry.
  `./scripts/lyre remote-host` runs the same host on a machine you own.

See [docs/remote-gpu.md](../remote-gpu.md) and [docs/runpod.md](../runpod.md),
and the [0.2.0 changelog](https://github.com/wizards-ecosystem/wizards-lyre/blob/v0.2.0/CHANGELOG.md).

## Release verification

The Remote GPU lane was verified live on 2026-09-26, twice, each time on a
fresh Runpod pod driven only through Lyre's own HTTP API (`POST
/api/remote-gpu/session`, real jobs through the SQLite queue and a
`LYRE_WORKER=remote` worker, then `DELETE /api/remote-gpu/session`):

| Component        | Verified configuration                                     |
| ---------------- | ---------------------------------------------------------- |
| GPU              | NVIDIA GeForce RTX 4090, 24 GB, Runpod Secure Cloud        |
| Rate             | $0.74/hr, read live from Runpod's catalog by Lyre          |
| Host image       | `wizards-lyre-remote-gpu:9b0ba2b1eb42` (second run)        |
| ACE-Step         | `14c0211d5a0653b0f63e27686f4c3f151b4d8629`                 |
| Local side       | Ubuntu 26.04 LTS under WSL2, Python 3.12                   |

| Run | Start -> ready | Generate | Cover of it | Spend |
| --- | --- | --- | --- | --- |
| 1: build `478130fd30e6`, 120 s tracks | 5 min 45 s | 47 s | 23 s | ~$0.09 |
| 2: shipping build `9b0ba2b1eb42`, 30 s tracks | 3 min 49 s | 15 s | 10 s | ~$0.05 |

Every take was 48 kHz stereo with audible signal and a quality score. The host
reported the checkout's own build id on the second run and a stale-build
warning on the first, as designed. After each Stop, Runpod's API returned 404
for the pod. Earlier live calls also found and fixed two problems no mock
could: Cloudflare in front of Runpod rejects Python's default user agent, and
the planned default GPU (RTX A5000) had no Secure stock, so the default is the
RTX 4090.

The production UI's new Remote GPU panel is covered by component tests; the
real-browser pass was **not** repeated for this release (no browser runtime was
available on the release machine).

The local ACE-Step path is unchanged from 0.1.0 apart from the worker asking a
backend for live readiness when it offers it. The 0.1.0 local hardware gates
(RTX 4070 Ti SUPER, WSL2) were **not re-run** for this release: that GPU was
occupied by another workload during release preparation. Treat local-GPU
behaviour as verified at 0.1.0 and the Remote GPU lane as verified here.

The locked Python and web suites, linters, type checks, license compliance,
dependency audits, source distributions, and reproducible runtime archives are
repeated by the tag workflow before it creates the draft release. The host
image's own workflow builds it, boots it, and checks it reports its build id.

## Security

- The ACE-Step overlay pins `anyio==4.14.2` and aligns `idna` with Lyre's lock.
- `accelerate` `PYSEC-2026-3804` (no fixed release yet) is a reviewed
  exception: Lyre never loads a checkpoint index it did not download itself.
- The Remote GPU host rejects every request without its secret before reading
  the body, refuses to start with a weak secret, and is only reached over HTTPS.
  A Runpod pod gets a secret made for that session; the API key never leaves
  your machine. See [SECURITY.md](https://github.com/wizards-ecosystem/wizards-lyre/blob/v0.2.0/SECURITY.md).

## Verify provenance

```bash
gh attestation verify wizards-lyre-0.2.0-linux-x86_64.tar.gz \
  --repo wizards-ecosystem/wizards-lyre
```

The 0.2.0 host image, `ghcr.io/wizards-ecosystem/wizards-lyre-remote-gpu:9b0ba2b1eb42`,
was pushed from the release-preparation machine so it could be tested live
before the release; it has no build attestation. Its tag is the host build id,
which the running host reports on `/health` and Lyre checks against your
checkout. Later host images are built, booted, pushed, and attested by the
**Remote GPU image** workflow.

## Supported boundary

- The Lyre server still binds only to `127.0.0.1` with no authentication.
- A Remote GPU is yours to operate: its account, spend, network exposure, and
  model licences. Stopping a rented pod is your job; a crash does not stop it.
- Everything in the [0.1.0 supported boundary](0.1.0.md#supported-boundary)
  still applies.
